1. WHAT THIS ROLE IS
------------------------------------------------------------------------------

  Account administration and oversight. Nothing else.

  Holds 4 of the 24 permissions. Reaches 35 of the 110 authenticated endpoints.
  State-wide: sees all 18 LGAs, no LGA filter applied. Do not render an LGA switcher.
  Rank 100 (highest). Rank decides WHO it can create, never WHAT it can do.

  STATE_ADMIN is the operational role: 24 permissions, all 110 endpoints.
  Anything to do with fishermen, assets, programmes or exports belongs there.

2. PERMISSIONS (exactly these four)
------------------------------------------------------------------------------

  user:manage         Create, amend, activate, suspend operator accounts
  user:assign_role    Set/change the role on an account (capped by rank)
  audit:read          Audit trail + enumerator activity
  dashboard:view      All dashboard and GIS surfaces

  Not held: fisherman:read, fisherman:create, fisherman:edit,
            fisherman:delete, fisherman:read_sensitive,
            registration:verify, registration:status, duplicate:resolve,
            duplicate:merge, asset:manage, asset:transfer,
            programme:manage, benefit:allocate, benefit:approve,
            benefit:deliver, cooperative:manage, community:manage,
            device:manage, sync:submit, report:export

5. HOW THE ACCOUNT EXISTS
------------------------------------------------------------------------------

  Created on the server only:

    npm run create:admin -- --email=x@crossriverstate.gov.ng \
                            --first=Ada --last=Effiom \
                            --role=SUPER_ADMIN

  There is NO API route that creates a SUPER_ADMIN. Account creation refuses
  any role at or above the caller's own rank, so even a Super Admin cannot
  create another one.

  => The role dropdown must NEVER list SUPER_ADMIN. The request always fails.

6. FIRST LOGIN - MANDATORY HANDLING
------------------------------------------------------------------------------

  POST /api/v1/auth/login returns mustChangePassword: true on an account
  using a password it was issued rather than chose.

  While that flag is true the token reaches ONLY these five:

    POST /api/v1/auth/change-password
    POST /api/v1/auth/logout
    POST /api/v1/auth/logout-all
    GET  /api/v1/auth/sessions
    GET  /api/v1/users/me

  Everything else returns 403 PASSWORD_CHANGE_REQUIRED.

  => Branch on mustChangePassword immediately after login and route to the
     change-password screen BEFORE loading any dashboard data. A dashboard
     that fetches its widgets first will get a wall of 403s.

  After a successful change every session is revoked, including the current
  one. Send the user back to the login screen.

7. LOGIN RESPONSE
------------------------------------------------------------------------------

  POST /api/v1/auth/login
  {
    "accessToken":       "<JWT, send as Authorization: Bearer ...>",
    "refreshToken":      "<opaque, rotated on every use, store securely>",
    "tokenType":         "Bearer",
    "expiresIn":         "15m",
    "refreshExpiresAt":  "<ISO date>",
    "mustChangePassword": false,
    "user": { "id", "email", "firstName", "lastName", "role", "status", "scope" }
  }

  Access token lasts 15 minutes. On 401 TOKEN_EXPIRED call
  POST /api/v1/auth/refresh with the refresh token and retry once.
  Refresh tokens rotate: always store the new one. Reusing an old one
  revokes the whole session family and forces a fresh login.

8. GET /api/v1/users/me - DRIVE THE NAVIGATION FROM THIS
------------------------------------------------------------------------------

  For a SUPER_ADMIN it returns:

    permissions: {
      isStateWide:          true,
      canManageUsers:       true,
      canReadAudit:         true,
      canVerify:            false,
      canManageProgrammes:  false,
      canExport:            false,
      canRegisterDevices:   false,
      canReadRegister:      false,
      granted: ["user:manage","user:assign_role","audit:read","dashboard:view"]
    }
    lgas: []        // empty, but isStateWide true means no filter is applied

  Use `granted` for anything the seven booleans do not cover. Every flag is
  read from the same permission set the routes are guarded on, so a true flag
  means the call will succeed.

9. ROLE PICKER RULES (POST /api/v1/users, PATCH /api/v1/users/:id)
------------------------------------------------------------------------------

  Ranks: SUPER_ADMIN 100, STATE_ADMIN 90, MINISTRY_OFFICER 80,
         LGA_ADMIN 60, COOPERATIVE_OFFICER 40, ENUMERATOR 20

  Rule: you may only assign a role STRICTLY BELOW your own rank.

  A Super Admin may therefore create:
    STATE_ADMIN, MINISTRY_OFFICER, LGA_ADMIN, COOPERATIVE_OFFICER,
    ENUMERATOR

  Never offer SUPER_ADMIN. Filter the dropdown by the signed-in user's rank
  rather than hard-coding the list, so it stays correct for other roles.

  Other constraints:
    - COOPERATIVE_OFFICER requires a `cooperative` id, else 400.
    - Omit `password` and the server generates one, returned ONCE in the
      response as `temporaryPassword`. It is not recoverable. Show it once
      and tell the admin to pass it on.
    - Every account created this way is flagged mustChangePassword, including
      when the admin supplies the password.
    - You cannot change your own role.
    - You cannot change your own account status.

10. ERROR CODES TO HANDLE
------------------------------------------------------------------------------

  401 TOKEN_MISSING             no Authorization header
  401 TOKEN_EXPIRED             refresh and retry once
  401 TOKEN_INVALID             sign out
  401 WRONG_TOKEN_TYPE          a refresh token was sent as an access token
  401 SESSION_REVOKED           signed out elsewhere, or password changed
  401 INVALID_CREDENTIALS       login failed (cause is deliberately not given)
  423 ACCOUNT_LOCKED            8 failed logins; locked 15 minutes
  403 PASSWORD_CHANGE_REQUIRED  temporary password still in use (section 6)
  403 MISSING_PERMISSION        role lacks the capability; do not retry
  403 ACCOUNT_INACTIVE          suspended or disabled
  403 ACCOUNT_PENDING           awaiting approval
  404 NOT_FOUND                 also returned instead of 403 when a record is
                                outside the caller's scope - do not infer that
                                the record does not exist
  409 EMAIL_TAKEN               account already exists
  422 VALIDATION_ERROR          field errors in `details`
  429 RATE_LIMITED              login is 10/15min per IP, reset 5/hr per IP

  All errors share one shape:
    { "success": false, "error": { "code", "message", "details"?, "requestId" } }

  Branch on `code`, never on `message`.
